## 2. 为什么要建分布式系统（Why）

| 动机 | 含义 |
| --- | --- |
| **更高性能 / 并行** | 很多 CPU、很多内存、很多磁盘臂并行工作 |
| **容错（fault tolerance）** | 两台机器做同样的事，一台挂了切到另一台 |
| **空间上天然分布** | 如纽约 A 银行 ↔ 伦敦 B 银行的跨行转账 |
| **安全 / 隔离** | 不信任的代码单独跑，只经狭窄网络协议交互 |

> ⚠️ **Morris 的第一条原则**：如果你能在一台电脑上解决，就**不要**建分布式系统。单机永远更简单。先试别的办法。

## 3. 为什么分布式系统难（Why Hard）

1. **并发（concurrency）**：系统的很多部分同时执行 → 会遇到全部并发编程问题（复杂交互、奇怪的时序依赖）。
2. **部分故障（partial failure）**：网络不可靠。单机是"要么工作要么崩"，多机则是**一部分坏了、另一部分还在跑**，还可能机器正常但网络某个环节坏了。这是根本性挑战。
3. **性能难以线性扩展**：想要 1000 台机器的性能，路上有很多路障；需要精心设计才能真正拿到"值得"的加速比。

**现实地位**：二十年前分布式系统只是学术 curiosities；如今（巨型网站驱动）已成为计算基础设施的核心。

## 4. 四大主题

### 4.1 实现（Implementation）——构建系统的工具

| 工具 | 作用 |
| --- | --- |
| **RPC** | 掩盖"在不可靠网络上通信"这一事实 |
| **线程（threads）** | 利用多核；更重要的是一种**构造并行操作**的编程方式 |
| **并发控制（锁等）** | 控制共享状态 |

这些在论文里都会出现，但**主要在 Lab 里大量实践**。

### 4.2 性能（Performance / Scalability）

- 核心概念：**可扩展的加速比（scalable speedup）**。
- 定义：加一台机器 → 时间减半，或吞吐翻倍。
- **为什么重要**：买机器（钱）比雇程序员重写代码（贵的路）便宜。
- **现实图景（Web 服务例子）**：
  ```
  users → Web Server 1..N → Database
  ```
  加 Web Server 能线性扩展，直到 **DB 成为瓶颈**——这时加 Web Server 无效。
  → 必须做设计工作：把单个 DB 拆成多个 DB（很麻烦，但很多人真的需要）。
- **结论**：可扩展性**很少是无限的**，瓶颈只是被移动了。

### 4.3 容错（Fault Tolerance）

**关键算术**：单机可稳定跑一年；1000 台机器 → 平均**每天约 3 台机器故障**。
> 规模把"极罕见事件"变成"持续发生的问题"。所以容错**必须内建于设计**。

两种常见口味：

| 概念 | 含义 |
| --- | --- |
| **可用性（Availability）** | 在**某类**故障下仍继续提供未损坏的服务；故障太多就停止响应 |
| **可恢复性（Recoverability）** | 故障时可能停止服务，但修复后能**不丢正确性**地继续 |

> 理想：既可用又可恢复。可用系统在故障过多时停止应答，修好后正确继续。

**两大容错工具**：

1. **非易失性存储（non-volatile storage）**：崩溃/断电后靠 checkpoint 或 log 恢复。难点在于写非易失存储很贵（机械盘要移臂+旋转），即使闪存也需要仔细设计才能高性能。
2. **复制（Replication）**：管理副本很棘手——核心风险是**两个副本意外失去同步**，就不再是副本了。**Lab 2 和 Lab 3 都是关于副本管理**。

### 4.4 一致性（Consistency）

以最简单的 **KV 服务**为例，只有两个操作：

```
put(key, value)   # 写入
get(key) -> value # 读取
```

**为什么一致性在分布式里变有趣**：因为有复制/缓存，同一份 key 会漂在多个地方。

**不一致的例子（论文级经典）**：
- 两个副本，key1 = 20。
- Client 发 `put(1, 21)` 给副本 1 → 副本 1 已更新为 21。
- 在发给副本 2 之前崩溃 → 副本 2 仍是 20。
- 之后 `get(1)` 可能读到 21，也可能读到 20（取决于问到谁）。

**一致性谱系**：

| 类型 | 保证 | 代价 |
| --- | --- | --- |
| **强一致性（strong）** | get 一定看到最近完成的 put | 读/写都要与所有副本通信，**昂贵** |
| **弱一致性（weak）** | 不做此保证，可能读到旧值 | 便宜，需附加语义才有用 |

**跨地域的代价**：副本要放在**失败概率独立**的地方（不同机架 → 同电源线一起死，是坏主意；应放不同城市/大洲）。但光速导致跨大洲通信要 **10–30ms**，而机器 1 秒能执行十亿条指令——等待就是巨大浪费。**这就是弱一致性方案的动机。**

## 6. MapReduce 案例研究（论文 2004）

### 6.1 背景与动机

- Google 要对**TB～PB 级数据**做计算：整个 Web 的索引、链接结构分析（找最重要/最权威的页面）、排序。
- 单机排序整个 Web 要几周到几年；必须在上千台机器上跑。
- 此前每个工程师都手写分布式代码，浪费稀缺的分布式专家精力。
- **目标**：让**非分布式专家**也能写大规模分布式计算——只需写 `Map` 和 `Reduce` 两个简单函数，框架处理其余一切。

### 6.2 编程模型（Abstraction）

```
Map(k1, v1)    -> list(k2, v2)
Reduce(k2, list(v2)) -> list(v2)
```

- 输入被切成**一大堆 split / 文件块**；框架在每个输入上并行跑 Map。
- 框架把所有 Map 输出中**同一个 key** 的实例收集到一起，调用一次 Reduce。

### 6.3 Word Count 示例

```
map(filename, content):
    for word in split(content):
        emit(word, "1")

reduce(word, values):
    emit(word, len(values))     # 只数字数，不看具体 value
```

- 输入示例：Map1 看到 "a b" → `(a,1) (b,1)`；Map2 看到 "b" → `(b,1)`；Map3 看到 "a c" → `(a,1) (c,1)`。
- 框架把所有的 `a` 收集给一次 reduce 调用，`b`、`c` 同理。
- **术语**：整个计算叫 **job**；一次 map/reduce 调用叫 **task**（map task / reduce task）。

### 6.4 系统结构（MapReduce 论文 Figure 1）

```
        Client ──提交 Job──▶ Master（单点，组织整个计算）
                                  │ 分配 map/reduce 任务
                                  ▼
        ┌─────────────── Worker 服务器（上千台）───────────────┐
        │  Map Worker：读输入 → 调用 map() → 输出写本地磁盘      │
        │  Reduce Worker：RPC 拉取自己负责的 key → 调用 reduce() │
        └──────────────────────────────────────────────────────┘
                                  │
                                  ▼
        GFS（集群文件系统）：输入与最终输出都存这里
```

流程（与 [[L1.1 - MapReduce 数据流动画版（分帧时间线）]] 一致）：

1. Master 分配 map 任务给 worker。
2. Worker 读输入，`map()` 对每次 `emit` 把数据**写到该 worker 的本地磁盘**。
3. Map 阶段结束，框架安排 shuffle：reduce worker 从**上千台** worker 中把属于自己 key 的中间数据**通过网络拉过来**。
4. Reduce worker 收集完所有数据后调用 `reduce()`；`reduce` 的 emit **写入 GFS**。

### 6.5 GFS 的角色

- 论文提到的 **GFS = Google File System**，集群文件系统，跑在**和 MapReduce 完全相同的那批机器**上。
- 大文件被**自动切成 64MB 的 chunk**，均匀散布到所有 GFS 服务器。
- 因此输入天然已经均匀分布 → 派 1000 个 map worker，每个读千分之一，并行读，获得千台服务器的总读取吞吐。

### 6.6 数据本地化（Data Locality）——关键的省网络技巧

2004 年的瓶颈是**网络吞吐**：

- 机架以太网交换机 → 汇聚到一个**根交换机**。
- 根交换机总吞吐分摊到约 2000 台机器，**每台机器仅约 50 Mbit/s**（相对磁盘/CPU 极小）。

于是设计上"站在自己头上"避免网络：

1. **GFS 与 MapReduce 跑在同一批机器**。Master 分配 map 任务时，会查 GFS 找出哪个服务器本地存着输入 split，**把任务派给同一台机器** → 默认情况下读输入是**本地磁盘**，不走网络。
2. **Map 输出写 map worker 本地磁盘** → 存的时候不需要网络。

> ✅ 再次强调：**Map 中间输出在本地磁盘，不在 GFS。**（见 [[L1 - MapReduce 与 GFS 架构]] 的纠错节）

### 6.7 Shuffle：唯一强制走网络的阶段

- 数据需要从"按行存储"（产生它的 map 机器上）转成"按列存储"（负责该 key 的 reduce 机器上）。
- 这就是 **shuffle**，**每一条数据都要过网络**，是 MapReduce 最贵的部分。
- 例：排序任务里输入 10TB → shuffle 网络传输 10TB。
- Reduce 输出也写 GFS：因为 GFS 为了性能要分片、为了容错要存 **2–3 个副本**，所以**至少一个副本必须跨网络写到别的服务器**。

### 6.8 MapReduce 的局限（讲师点评）

| 局限 | 说明 |
| --- | --- |
| 每个 map 必须**完全独立** | map 只看自己的参数，不能依赖别的 |
| 只适合 `map → shuffle → reduce` | 复杂管道要拆成多个 job（如 **PageRank** 迭代多次） |
| **批处理同步屏障** | 必须等所有 map 完成才能 shuffle（对应 [[L1.1 - MapReduce 数据流动画版（分帧时间线）]] 的 Frame 6） |
| 中间状态反复落盘 | 现代后继系统改用**流式 / DAG**，能更好优化，但会牺牲编程简洁性 |

### 6.9 现代变化

- 现代数据中心网络：**多个根交换机**（不再单根），每机架交换机连到每个根，流量分摊 → 吞吐大增。
- Google 多年前已停用 MapReduce。
- 停用前，新版实现**不再执着于数据本地化**，乐意从任何地方加载数据，因为"假定网络非常快"。

## 7. 一句话总结

> **能用单机就别分布式。** 分布式系统的难点 = 并发 + 部分故障 + 难以线性扩展。
> 它的两大工具是**非易失存储**和**复制**；它最贵的语义是**强一致性**。
> MapReduce 的漂亮之处在于：把"如何在千台机器上跑 + 搬数据 + 容忍故障"全部藏进框架，程序员只写 `map` 和 `reduce`；而其性能秘诀是**数据本地化 + shuffle 之外绝不上网**（中间结果留在本地磁盘）。
